## 1. Level 1과 Level 2의 일을 구별하기

회사 건물에 들어오는 상황을 생각해 봅시다.

Level 2는 입구에서 “정말 이 직원이 맞나요?”를 확인합니다.
아이디와 비밀번호를 검사하거나 회사 SSO를 이용하고, 이후 요청의 세션이나 토큰을 검증합니다.

Level 1은 확인된 직원에게 “이 메뉴를 읽어도 되나요?”, “이 저장 버튼을 실행해도 되나요?”를 판단합니다.
또한 여러 업무가 공통으로 사용하는 회사·사용자·메뉴·메시지와 기준정보를 제공합니다.

| 기능 | 담당 범위 | 이번 문서 갱신 시점 |
|---|---|---|
| 조직·사용자·ROLE·메뉴·버튼 권한 | Level 1 | 기존 구현 |
| 공통코드·다국어·공통 오류 | Level 1 | 기존 구현 |
| 단위 `TB_UNIT` | Level 1 | 승인된 확장 설계, 후속 구현 |
| 통화 `TB_CURRENCY` | Level 1 | 승인된 확장 설계, 후속 구현 |
| 금액 표시 `TB_MENU_AMOUNT_FORMAT` | Level 1 | 승인된 확장 설계, 후속 구현 |
| 실제 로그인·비밀번호 검사·세션·토큰·SSO | Level 2 | 후속 구현 |
| 품목별 포장 환산·재고 수불·환율 적용 원가 계산 | 해당 업무 | 후속 업무 구현 |

단위·통화·금액 표시가 새로 필요하다고 인증 Starter 안에 같은 목적의 테이블을 만들지 않습니다.
LOCAL 로그인, Session, JWT, SSO 등 인증 방식이 달라져도 같은 Level 1 기준정보를 사용합니다.

### 1.1 Java 파일의 위치도 역할을 구별한다

신규 구현은 기능 아래 `controller`, `service`, `model`, `mapper`, `config`처럼
역할별로 구분하는 프로젝트 관례를 따릅니다.
실제 로그인 기능은 향후 `auth/controller`, `auth/service`, `auth/model`, `auth/mapper`, `auth/config`
구조로 구성할 수 있습니다. 이 폴더와 클래스들이 현재 구현되어 있다는 뜻은 아닙니다.

오류·다국어·권한 기능은 기존 공통 구현을 재사용합니다.
이번 문서 추가로 기존 Java 패키지를 이동하거나 기존 폴더를 재구성하지 않습니다.

## 2. 검증된 사용자 번호를 연결하기

### 2.1 CurrentUserProvider.java의 userId()

기존 [CurrentUserProvider.java](F:/java/workspace/erpcom/src/main/java/com/erpcom/erpcom/common/web/CurrentUserProvider.java)에는
다음 메서드 약속이 있습니다.

```java
Long userId(HttpServletRequest request);
```

뜻은 “이 요청에서 신분이 확인된 사람의 TB_USER.USER_ID를 알려 주세요”입니다.
Level 2 구현은 검증된 인증 컨텍스트·세션·토큰에서 그 번호를 가져와야 합니다.
검증되지 않은 `X-User-Id` 같은 요청 헤더나 요청 본문의 사용자 번호를 신분 증거로 사용하지 않습니다.
미인증 요청에는 null을 반환합니다.

예를 들어 검증된 세션의 사용자 번호가 123이면 이 메서드가 123을 돌려줍니다.
사용자가 요청 본문에 999를 적더라도 그것만으로 999번 사용자로 실행하면 안 됩니다.

### 2.2 RequestUserService.java의 require()

기존 [RequestUserService.java](F:/java/workspace/erpcom/src/main/java/com/erpcom/erpcom/common/web/RequestUserService.java)의
`require(request)`는 다음 순서로 처리합니다.

1. `provider.userId(request)`로 현재 사용자 번호를 받습니다.
2. 값이 null 또는 0 이하이면 `ERR_AUTH_REQUIRED`를 발생시킵니다.
3. `PermissionService.user(id)`로 공통 사용자와 소속의 유효성을 확인합니다.
4. 확인된 사용자 정보를 다음 처리에 전달합니다.

따라서 토큰에 번호가 있다는 사실만으로 모든 요청이 허용되지 않습니다.
사용자·회사·선택 소속의 유효성과 실제 메뉴·버튼 권한을 Level 1에서 확인해야 합니다.

### 2.3 지금 로그인 구현이 없을 때

기존 [CommonWebConfiguration.java](F:/java/workspace/erpcom/src/main/java/com/erpcom/erpcom/common/web/CommonWebConfiguration.java)의
`unauthenticatedUserProvider()`는 기본적으로 null을 반환하는 제공자입니다.
Level 2가 `CurrentUserProvider` 타입의 검증된 제공자를 연결해야 합니다.

개인 설정에 SSO enabled나 관리자 초기화 enabled 값을 적었다고 이 제공자가 자동으로 로그인 기능을 갖지는 않습니다.
새 기준정보를 문서에 추가한 것만으로 관리자 API를 로그인 없이 사용할 수도 없습니다.

## 3. 새 기준정보의 조회와 변경을 보호하기

### 3.1 인증 다음에는 메뉴·버튼 권한을 확인한다

단위·통화·금액 표시 설정의 관리 창구에도 기존 Backend 권한 정책을 적용합니다.
중앙 공통 관리에서는 `COMMON_ADMIN`과 조회·신규·저장·비활성화에 대응하는 기능 버튼 권한을 재사용합니다.

기존 연결 지점은 다음과 같습니다.

| 파일·메서드 | 역할 |
|---|---|
| `RequestUserService.java`의 `require()` | 현재 인증 사용자 확인 |
| `CommonWebConfiguration.java`의 `preHandle()` | `@RequiresPermission`을 읽고 Controller 실행 전 검사 |
| `PermissionServiceImpl.java`의 `requireButton()` | 메뉴와 해당 기능 버튼 실행권한 확인 |
| `PermissionServiceImpl.java`의 `requireScope()` | 요구한 접근 범위 확인 |
| `PermissionServiceImpl.java`의 `requireData()` | 업무 대상의 실제 회사·사업장·부서·소유자 범위 확인 |

현재 공통 권한 인터셉터의 연결 경로는 `/api/common/**`입니다.
후속 API를 다른 경로로 만든다면 인터셉터 연결을 확장하거나 Service에서 권한 검사를 연결해야 합니다.
어노테이션을 붙인 것만으로 경로 밖의 API가 보호된다고 가정하지 않습니다.

### 3.2 실제 예 1: 단위를 등록하는 관리자

아래는 후속 기능 구현 후의 처리 예시입니다. 현재 단위 등록 API가 있다는 뜻은 아닙니다.

```text
관리자가 KG 단위를 등록하려고 요청
  ↓ Level 2가 로그인 세션 또는 토큰을 검증
검증된 사용자 번호 123 제공
  ↓ Level 1이 사용자와 COMMON_ADMIN 기능 권한 검사
환산 기준 G, 계수 1000, 소수 자릿수의 유효성 검사
  ↓
CREATED_BY=123으로 등록
```

CREATED_BY를 요청자가 임의로 지정하게 하지 않습니다.
후속 Migration이 공통 기준자료를 넣을 때만 시스템 생성자 예약값 0을 사용합니다.

### 3.3 실제 예 2: 억원 표시 설정을 변경하는 관리자

관리자가 총예정원가 항목의 표시 소수 자릿수를 1에서 2로 변경한다고 해 봅시다.

```text
Level 2: 누구인지 확인
Level 1 권한: 이 관리 설정을 저장할 수 있는지 확인
Level 1 입력 검사: 메뉴·항목·통화·배율·자릿수·반올림 규칙 확인
Level 1 버전 검사: 읽었던 VERSION_NO와 현재 버전이 같은지 확인
저장: UPDATED_BY에 실제 사용자 번호 기록, VERSION_NO 증가
```

통화나 표시 설정의 값이 올바르다는 검증과 사용자가 변경할 권한이 있다는 검증은 둘 다 필요합니다.
화면의 저장 버튼을 숨겨도 Backend 검사를 생략하지 않습니다.

## 4. 단위·통화·금액 표시를 재사용하기

### 4.1 UNIT은 Level 1 기준정보를 이용한다

Level 2에서 EA·PCS·KG·G 목록이나 KG→G 환산계수를 다시 정의하지 않습니다.
후속 Level 1 구현이 단위 종류·소수 수량 정밀도·공통 환산 기준을 제공합니다.

예를 들어 `1.25 KG = 1250 G`는 공통 환산 기준을 사용할 수 있습니다.
볼펜의 `1 BOX = 12 EA`와 음료의 `1 BOX = 24 EA`는 품목별 관계이므로 재고 업무에서 관리합니다.
MB/GB와 MiB/GiB 구분도 Level 1의 단위 정의를 그대로 사용합니다.

### 4.2 CURRENCY 테이블과 record는 역할이 다르다

지원 통화 목록은 후속 `TB_CURRENCY`가 원본입니다.
조회한 자료는 `CurrencyInfo` 같은 record에 담아 전달할 수 있습니다.
이 이름은 설계 예시이며 현재 Java 클래스가 아닙니다.

```text
DB: KRW, 기본 소수 자릿수 0, 이름 메시지 코드 보관
Level 1 조회·번역: CurrencyInfo("KRW", "대한민국 원", 0)으로 전달
Level 2: 이 통화 목록을 인증 코드 안에 복제하지 않음
```

통화 기호나 요청 언어만으로 실제 통화를 결정하지 않습니다.
통화 목록을 로그인 코드의 enum이나 고정 record 목록으로 두지도 않습니다.

### 4.3 화면 표시 설정은 실제 금액을 바꾸지 않는다

총예정원가 예:

```text
실제 금액: 59,230,000,000 KRW
메뉴·항목 설정: 배율 100,000,000, 표시 소수 1자리
표시 결과: 592.3 (단위: KRW 억)
```

KRW의 기본 소수 자릿수 0과 억원 화면의 표시 자릿수 1은 서로 다른 설정입니다.
내부 계산 정밀도까지 화면 자릿수에 맞춰 줄이지 않습니다.
금액·소수 수량·환산계수는 BigDecimal과 적절한 DB 숫자 정밀도로 처리합니다.
원본은 보존하고 화면·보고서·Excel에 같은 표시·반올림 정책을 적용합니다.

후속 Level 1 서비스가 메뉴·항목 설정을 해석하고 화면에 전달합니다.
현재 `ReferenceDataServiceImpl.java`의 `bootstrap()`에는 이 표시 설정이 없습니다.
확장된 bootstrap 응답으로 제공할지 별도 조회로 제공할지는 실제 구현에서 결정합니다.

### 4.4 메뉴 설정 조회와 업무 금액 조회 권한을 구별한다

‘이 화면은 억원·소수 1자리로 표시한다’는 설정을 읽었다고 실제 원가를 읽을 권한까지 생기지는 않습니다.
업무 API는 메뉴·버튼과 실제 자료 범위를 별도로 검사해야 합니다.
대상의 회사·부서·소유자 번호는 Backend가 DB에서 확인하고 요청자가 주장한 번호를 그대로 믿지 않습니다.
목록 조회도 유효한 권한 범위에 맞춰 DB 조회 조건을 제한합니다.

고정 KRW 화면에서 실제 자료가 USD이면 표시 문구만 KRW로 바꾸면 안 됩니다.
서로 다른 통화를 합산하는 일에는 적용 날짜·환율 등의 별도 업무 정책이 필요합니다.
환율 업무는 로그인이나 화면 표시 배율이 대신하지 않습니다.

## 5. 언어·로그인 정보·설정 갱신을 구별하기

### 5.1 언어 선택은 경제적 단위 변환이 아니다

단위명·통화명·표시 배율 문구는 기존 `MessageService`와 다국어 테이블을 재사용합니다.
예를 들어 한국어와 영어에서 통화 이름이나 메뉴 이름을 다르게 보여 줄 수 있습니다.
숫자의 구분 기호도 언어·지역 표시에 맞출 수 있습니다.

하지만 한국어에서 영어로 바꾼다고 원화가 달러로 바뀌거나 실제 금액이 달라지지 않습니다.
언어별 금액 설정 테이블이나 `AMOUNT_UNIT_KO`, `AMOUNT_UNIT_EN` 같은 컬럼을 만들지 않습니다.

### 5.2 인증 토큰·세션에 기준정보 전체를 고정하지 않는다

검증된 신분을 전달하는 일과 최신 기준정보를 읽는 일은 구별합니다.
단위·통화·메뉴 표시 정책 전체를 로그인 시점의 토큰이나 세션에 고정하면,
관리자가 소수 자릿수를 바꾸어도 로그인 당시 설정이 계속 사용될 수 있습니다.

후속 구현에서는 Level 1 서비스에서 최신 유효 설정을 조회합니다.
장기 캐시가 필요하면 설정 변경 트랜잭션의 커밋 후 관련 조회·표시 정책 캐시를 무효화합니다.
여러 서버를 사용하는 경우에도 변경 반영 정책을 정해야 합니다.
현재 새 기준정보 캐시나 무효화 코드가 구현되었다는 뜻은 아닙니다.

<a id="chapter-6"></a>
## 6. 오류와 최초 관리자 준비

### 6.1 인증 단계의 오류도 같은 형식으로 응답한다

Level 2 인증 필터의 오류 처리는 기존 `ApiErrorWriter.java`의
`write(request, response, exception)`과 `MessageService`를 재사용합니다.
로그인 구현 안에 별도의 번역문·HTTP 상태 정책을 중복 하드코딩하지 않습니다.

| 상황 | 기존 메시지 코드 |
|---|---|
| 인증되지 않은 요청 | `ERR_AUTH_REQUIRED` |
| 인증되었지만 기능 실행 거부 | `ERR_ACCESS_DENIED` |
| 내부 처리 오류 | `ERR_INTERNAL_SERVER` |

새 단위·통화 입력 오류의 사용자 안내도 공통 메시지 코드 정책을 따릅니다.
비밀번호·토큰·내부 예외 문자열을 사용자 오류 메시지의 인자로 넘기지 않습니다.

### 6.2 기준정보 Seed와 로그인 계정 생성은 다르다

기존 V003은 ROLE 10의 COMMON_ADMIN 메뉴·버튼 권한 예제를 준비하지만,
로그인 가능한 실제 사용자와 사용자-ROLE 연결을 자동 생성하지 않습니다.

새 단위·통화 Seed를 추가해도 관리자 로그인 계정이 생기는 것은 아닙니다.
실제 계정과 역할 배정은 고객별 후속 Migration 또는 권한 있는 운영 등록 절차에서 준비합니다.
실제 비밀번호 해시는 후속 Level 2의 비밀번호 처리 구현으로 생성하고 평문을 저장하지 않습니다.

`application-dev.yaml`의 인증·SSO·관리자 초기화 관련 값은 현재 예약 설정입니다.
값을 실제로 검증하고 로그인·세션·SSO를 수행하는 책임은 후속 Level 2 구현에 있습니다.
개인 설정 파일의 비밀 값을 문서나 저장소에 복사하지 않습니다.

## 7. 후속 구현 순서와 확인할 사항

이 문서 수정 다음에 실제 구현을 진행한다면 다음 순서를 권장합니다.

1. Level 1 후속 Migration으로 세 테이블·제약·공통 5개 컬럼·VERSION_NO를 추가합니다.
2. 표준 단위·지원 통화·분류·다국어 메시지를 준비하고 고객별 메뉴 표시 설정은 분리합니다.
3. 기존 Controller → Service → ServiceImpl → Mapper 계층으로 조회·관리와 소수형 검증을 구현합니다.
4. Level 2 인증 구현이 검증된 USER_ID를 CurrentUserProvider로 제공합니다.
5. 새 관리 창구에 메뉴·버튼 권한, 감사 기록, 변경 충돌 검사를 연결합니다.
6. 화면·보고서·Excel이 같은 원본 금액과 표시 정책을 사용하게 연결합니다.

세 영역의 자세한 컬럼·환산 예제·계산 예제·기존 Java 연결 지점은
[ErpComLevel1.md의 17장](F:/java/workspace/erpcom/docs/ErpComLevel1.md#chapter-17)에 있습니다.

후속 구현 검증에서는 다음 사례를 확인해야 합니다. **이번 문서 수정에서 실행한 테스트 목록은 아닙니다.**

| 확인할 사례 | 기대하는 결과 |
|---|---|
| 로그인 없이 기준정보 관리 요청 | 인증 필요 오류 |
| 인증되었지만 저장 버튼 권한이 없는 사용자 | 실행 거부 |
| 임의 사용자 번호를 본문·헤더에 넣음 | 인증된 신분을 대체하지 않음 |
| 단위·통화·금액 표시 설정 변경 | 실제 인증 사용자 감사 기록과 버전 검사 |
| 잘못된 단위 종류·환산계수·자릿수·참조 | Backend 입력 검증 거부 |
| 59,230,000,000 KRW를 억원·소수 1자리 표시 | 592.3 표시, 실제 금액 보존 |
| 원화 화면에 달러 자료를 전달 | 통화 불일치를 확인하며 환율 없이 원화로 표시하지 않음 |
| 표시 소수 1자리에서 2자리로 변경 | 갱신 정책에 맞춰 화면·보고서·Excel에 새 설정 반영 |
| 단위나 통화를 비활성화 | 신규 사용 정책 검사, 과거 참조 보존 |

현재 인증 연결의 간단한 계약은
